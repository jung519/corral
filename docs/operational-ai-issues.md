# P0 — 원격 제어평면

## [OPS-01] 코어 원격 제어평면(WS) 신설

**목적**
코어는 현재 부모 프로세스의 IPC 채널로만 제어된다(`ipc-host.ts`). VM에 두고 원격에서
조작하려면 네트워크 전송이 필요하다. **운영 AI의 모든 작업이 이것에 막혀 있다.**

**범위**
- 기존 `startIpcHost`의 요청/응답·이벤트 스트림 **프로토콜은 그대로 두고 전송만 추가**한다
  (`{kind:'req'|'res'|'event'}`).
- WS 서버를 코어에 추가하고, 프로세스 IPC와 **동시에** 동작하게 한다(로컬 모드 무영향).
- 기본 바인딩 `127.0.0.1`, 포트·바인딩은 설정으로 변경 가능(D18).
- 외부 바인딩은 **명시적 옵트인**이며, 옵트인 시 경고를 로그에 남긴다.

**수용 기준**
- 로컬 데스크톱 실행이 기존과 동일하게 동작한다(회귀 없음).
- WS로 접속해 `state`·`start` 등 기존 메서드를 호출하면 IPC와 같은 결과가 온다.
- 이벤트 스트림이 WS 클라이언트에도 전달된다.
- 기본 설정에서 외부 인터페이스에 포트가 열리지 않는다.

**참고**: `src/ipc-host.ts`, `src/ipc-main.ts`

## [OPS-02] 페어링 코드 인증

**목적**
원격 접속에 인증이 필요하다. 긴 토큰을 복사·붙여넣지 않고 연결할 수 있어야 한다(D17).

**범위**
- 최초 연결 시 코어가 **짧은 1회용 코드**를 발급해 로그/콘솔에 표시.
- 클라이언트가 코드를 제출하면 **장기 토큰을 발급**하고 클라이언트가 저장.
- 이후 연결은 토큰으로 인증. 코드는 짧은 유효시간 후 만료.
- 토큰 저장은 파일(0600). 재발급·폐기 경로 제공.
- 인증 실패 시 연결을 즉시 끊는다.

**수용 기준**
- 코드 없이 접속하면 거부된다.
- 잘못된 코드는 거부되고, 시도 횟수가 제한된다.
- 페어링 후 재시작해도 저장된 토큰으로 재연결된다.
- 토큰 폐기 후에는 기존 클라이언트가 거부된다.

**선행**: OPS-01

---

## [OPS-03] 데스크톱 원격 코어 접속 모드

**목적**
데스크톱 앱은 지금 **자기가 코어를 spawn**한다. 원격 코어에 접속하는 선택지가 필요하다(D3).

**범위**
- 설정에 **로컬 코어 / 원격 코어** 선택 추가(주소 + 페어링).
- 원격이면 spawn을 건너뛰고 WS로 접속. `callCore`·이벤트 relay를 전송만 교체.
- **renderer는 수정하지 않는다**(`window.corral` 인터페이스 유지).
- 연결 상태(연결됨/끊김/재연결 중)를 UI에 표시하고 자동 재연결한다.

**수용 기준**
- 로컬 모드는 기존과 동일하게 동작한다.
- 원격 모드에서 대시보드·승인·이벤트가 모두 정상 동작한다.
- 코어 재시작 시 앱이 자동 재연결한다.

**선행**: OPS-01, OPS-02
**참고**: `desktop/src/orchestrator-process.ts`, `desktop/src/main.ts`

## [OPS-04] 원격 모드 네이티브 기능 라우팅

**목적**
`window.corral`의 네이티브 기능이 원격 모드에서 **어느 머신을 향할지** 정해져야 한다(설계 §6.3).

**범위**
- **원격(코어)로 보낼 것**: 설정·시크릿·방향성·드래프트, Docker/CLI 감지
  → 코어에 해당 메서드 추가.
- **로컬에 남길 것**: 프로바이더 로그인 캡처(브라우저가 로컬에 있다), OS 알림, 앱 버전.
- 로그인 캡처 결과(토큰)는 **원격 코어의 시크릿으로 저장**되어야 한다.
- 원격 모드에서 시크릿 저장은 키체인이 아니라 **파일 스토어**를 사용한다.

**수용 기준**
- 원격 모드에서 설정 마법사가 끝까지 진행된다.
- 로컬에서 Claude 로그인 버튼을 눌러 얻은 토큰이 원격 코어에 저장된다.
- 원격 모드에서 Docker/CLI 감지 결과가 **VM 기준**으로 표시된다.

**선행**: OPS-03

# P1 — 헤드리스 실행

## [OPS-05] 헤드리스 실행 엔트리 복구

**목적**
현재 코어는 **Electron이 fork해야만** 제어가 된다. 단독 실행하면 오케스트레이터는 뜨지만
승인·조작이 불가능하다. VM 배포의 전제 조건이다.

**범위**
- 헤드리스 엔트리와 실행 스크립트를 만든다(설정 파일 경로를 인자로 받는다).
- 프로세스 IPC가 없으면 **WS 제어평면만으로** 동작해야 한다(OPS-01 의존).
- 종료 시그널 처리(진행 중 작업 정리).

**수용 기준**
- Node로 단독 실행 후 원격 클라이언트를 붙여 이슈 승인까지 가능하다.
- 프로세스 IPC 없이도 오류 없이 기동한다.
- SIGTERM에 정상 종료한다.

**선행**: OPS-01

---

## [OPS-06] README 정정 + VM 배포 문서

**목적**
README의 "Run headless" 절차는 **현재 사실이 아니다**(엔트리·스크립트 없음). 잘못된 문서가
남아 있으면 사용자가 막힌다.

**범위**
- README의 헤드리스 절을 실제 동작하는 절차로 교체.
- VM 배포 가이드 신설: 상시 실행(systemd 등), 환경변수/파일 시크릿, Docker 준비,
  프로바이더 인증(로컬에서 캡처해 주입 / device 인증), 원격 접속·터널 설정.

**수용 기준**
- 문서만 보고 빈 VM에서 기동·접속까지 가능하다.
- 문서의 모든 명령이 실제로 동작한다(검증 후 기재).

**선행**: OPS-05

# P2 — 파이프라인 런타임

## [OPS-07] 파이프라인 정의 스키마·로더

**목적**
파이프라인(트리거 → 입력 → AI → 출력)을 **선언으로 정의**한다(D9). 스키마가 이후 모든
작업의 계약이 된다.

**범위**
- 스키마 정의(검증 포함)와 로더. 필드는 **도메인 중립 이름**만 사용한다.
- 잘못된 정의는 **기동 시점에** 명확한 메시지로 거부한다.
- 선언 스키마는 **코드 오퍼레이션의 부분집합**이 되도록 설계한다(D10, OPS-23 대비).
- 설계서 §5의 초안을 기준으로 하되, 실제 검증에서 드러난 차이는 문서에 반영한다.

**수용 기준**
- 유효한 정의가 로드되고, 각 필드가 런타임 값으로 해석된다.
- 필수 필드 누락·타입 불일치·알 수 없는 어댑터 종류가 각각 다른 메시지로 거부된다.
- 스키마에 특정 도메인 용어가 없다.

**참고**: `operational-ai-design.md` §5

---

## [OPS-08] 파이프라인 레지스트리·실행 수명주기

**목적**
파이프라인을 등록하고, **실행 1건**의 수명주기를 관리한다.

**범위**
- 레지스트리(등록·조회·활성/비활성).
- 실행 수명주기: 수신 → 입력 해석 → AI → 검증 → 출력 → 종료, 각 단계 실패 처리.
- 동시 실행 수 제한(정의값, 기본 1 — 한도를 모르면 낮게 시작).
- 실행 상태를 이벤트로 발행(기존 이벤트 버스 재사용, **단위는 이슈가 아니라 실행**).
- **중복 처리 방어**: `skip_if` 조건 만족 시 AI를 호출하지 않는다.

**수용 기준**
- 같은 이벤트가 두 번 와도 조건이 맞으면 AI를 호출하지 않는다.
- 각 단계 실패가 구분되어 기록된다(입력 실패 / AI 실패 / 검증 탈락 / 출력 실패).
- 동시 실행이 설정값을 넘지 않는다.

**선행**: OPS-07

---

## [OPS-09] 실행 이력 저장소(JSONL)

**목적**
운영 AI는 실행 단위가 많다. 조회 가능한 이력이 필요하다(D15).

**범위**
- `OpsHistoryStore` 인터페이스를 먼저 정의한다(D16 — 나중에 교체 가능하게).
- 일별 롤링 JSONL + 일별 집계(건수·토큰·비용·폴오버·저신뢰·실패).
- 보관 기간 초과 파일 정리.
- **네이티브 모듈을 추가하지 않는다**(크로스빌드 유지).

**수용 기준**
- 실행 1건이 1줄로 기록된다(파이프라인·결과·토큰·소요시간·프로바이더 포함).
- 일별 집계가 실행 결과와 일치한다.
- 최근 N일 범위 조회가 동작한다.
- 새 런타임 의존성이 추가되지 않는다.

**선행**: OPS-08

---

## [OPS-10] 수동 실행 경로

**목적**
트리거 어댑터가 없어도 파이프라인을 **직접 실행**해 검증할 수 있어야 한다. 재처리에도 쓴다.

**범위**
- 제어평면 메서드 추가: 파이프라인 키 + 입력(식별자 또는 본문)으로 1건 실행.
- 결과를 호출자에게 반환하고 이력에도 남긴다.

**수용 기준**
- 트리거 설정 없이 파이프라인 1건을 실행하고 결과를 확인할 수 있다.
- 실행 결과가 이력에 남는다.

**선행**: OPS-08

# P3 — AI 오퍼레이션

## [OPS-11] 1턴 구조화 출력 실행기

**목적**
개발 AI는 멀티턴 도구 루프지만, 운영 AI는 **1턴에 구조화된 JSON**을 받는다. corral에는
이 경로가 없다.

**범위**
- 프롬프트(시스템·사용자 템플릿) 조립 + 출력 스키마 지정 + 응답 파싱.
- 기존 프로바이더 계층(폴오버 포함)을 **재사용**한다 — 새로 만들지 않는다.
- 토큰 사용량·프로바이더·폴오버 여부·소요시간을 결과에 담는다.
- 스키마 불만족은 **폴오버 대상**으로 취급한다(다른 프로바이더는 지킬 수 있다).

**수용 기준**
- 스키마를 준 호출이 검증된 객체를 반환한다.
- 1차 프로바이더 실패 시 폴오버되고 결과에 표시된다.
- 응답이 스키마를 만족하지 못하면 폴오버가 시도된다.

**선행**: OPS-07

---

## [OPS-12] 응답 JSON 복구

**목적**
구조화 출력을 강제해도 프로바이더에 따라 코드펜스·여분 문자가 섞여 나온다. 그대로 실패
처리하면 **정상 결과를 버리게 된다**.

**범위**
- 코드펜스 제거.
- 첫 `{`부터 **괄호 균형이 맞는 지점까지** 잘라 재파싱(문자열 리터럴 안의 괄호는 세지 않는다).
- 그래도 실패하면 스키마 오류로 올린다(폴오버 대상).

**수용 기준**
- 펜스로 감싼 응답이 파싱된다.
- JSON 뒤에 잉여 문자가 붙은 응답이 파싱된다.
- 문자열 값 안에 중괄호가 있어도 잘못 자르지 않는다.
- 잘린(불완전) 응답은 복구하지 않고 실패로 올린다.

**선행**: OPS-11

---

## [OPS-13] 출력 검증 규칙 엔진

**목적**
**AI를 믿지 않는다.** 프롬프트에 규칙을 적어도 코드에서 다시 검사한다 — 모델을 바꾸면
프롬프트 준수는 깨질 수 있다.

**범위** (전부 도메인 중립)
- `allowed_values` — 허용 목록 밖 값은 버리고 **버린 값을 기록**한다. 목록은 외부에서 조회
  가능해야 한다(정본이 우리 쪽에 없을 수 있다).
- `max_items` — 개수 상한을 코드에서도 자른다.
- `min_confidence` — 임계 미만이면 **출력을 내보내지 않고** 저신뢰로 기록한다.
- `derive` — AI에 묻지 않고 코드로 파생 필드를 계산한다.
- `skip_if` — 이미 처리된 대상은 AI 호출 전에 건너뛴다.

**수용 기준**
- 허용 목록 밖 값이 결과에서 제외되고 버린 목록이 이력에 남는다.
- 상한을 넘는 개수가 잘린다.
- 임계 미만 결과가 출력 단계로 넘어가지 않는다.
- 파생 필드가 규칙대로 계산된다.

**선행**: OPS-11

---

## [OPS-14] 토큰 상한 통합(개발·운영 공유)

**목적**
상한 단위를 **토큰**으로 통일하고, 개발 AI와 운영 AI가 **하나의 상한을 공유**한다.
한쪽이 소진하면 둘 다 멈춘다(D11, D12).

**범위**
- 일일 입력/출력 토큰 상한(설정으로 조정 가능).
- **호출 전 확인** — 초과면 호출하지 않고 전용 오류로 중단한다.
- 소진율 경계(예: 50/80/100%) 도달 시 **경계를 넘는 순간 한 번만** 알린다.
- 상한 초과로 처리하지 못한 건은 **재시도 폭주를 만들지 않는다**(버리고, 다음 기회에 다시 대상).
- 기존 개발 AI 비용 집계와 **하나의 카운터**로 합친다.

**수용 기준**
- 개발 AI 사용량이 운영 AI 상한 판단에 반영된다(그 반대도).
- 상한 도달 후 AI 호출이 차단된다.
- 경계 알림이 중복 발송되지 않는다.
- 상한 초과 건이 무한 재시도되지 않는다.

**선행**: OPS-09

---

# P4 — 어댑터

## [OPS-15] 트리거 어댑터 축 + 스케줄

**목적**
일감 수신 방식을 **어댑터 축**으로 정의한다(기존 5축과 동일한 패턴).

**범위**
- 트리거 인터페이스 + 레지스트리(`kind`로 선택).
- 기본 구현: **수동**(OPS-10 재사용), **스케줄**(주기 실행).
- 구독 시작/중지가 파이프라인 활성/비활성과 연결된다.

**수용 기준**
- 정의의 `kind`에 따라 트리거가 선택된다.
- 스케줄 트리거가 지정 주기로 실행을 만든다.
- 비활성화하면 트리거가 멈춘다.

**선행**: OPS-08

---

## [OPS-16] Pub/Sub 트리거 어댑터

**목적**
첫 실전 트리거. **포트를 열지 않고** 일감을 받는다(D5).

**범위**
- 구독 수신 → 실행 생성. 동시 수신 수 제한.
- **확인/재전송 정책**: 형식이 잘못된 메시지·상한 초과·대상 없음은 **버린다**(재시도해도
  같은 결과 → 무한 재전송 방지). 일시적 실패만 재전송을 요청한다.
- 무한 재시도 방어는 **코드 카운터가 아니라 큐의 dead-letter 정책**에 맡긴다.
- 로컬 개발용 에뮬레이터 경로.

**수용 기준**
- 메시지 수신 시 실행이 생성된다.
- 잘못된 형식 메시지가 재전송 루프를 만들지 않는다.
- 상한 초과 시 메시지를 버리고 다음 기회에 재처리된다.
- 종료 시 처리 중이던 메시지가 유실되지 않는다.

**선행**: OPS-15

---

## [OPS-17] 입력 해석기(none·http)

**목적**
이벤트에는 **식별자만** 온다. corral이 **처리 시점에** 입력을 조회해야 최신값을 쓴다(D6).

**범위**
- 인터페이스: `(이벤트, 정의) → 납작한 입력 객체`.
- `none` — 이벤트 본문을 그대로 사용.
- `http` — method·URL 템플릿·헤더·본문 템플릿·응답 필드 매핑. **REST와 GraphQL을 모두 덮는다**
  (GraphQL은 POST + JSON 본문).
- `require` 필드 누락 시 실행을 건너뛴다(재시도하지 않는다).
- 시크릿은 설정에 직접 쓰지 않고 참조로 주입한다.

**수용 기준**
- 식별자만 있는 이벤트로 외부 조회 후 입력이 구성된다.
- 같은 정의로 GraphQL 엔드포인트에서도 입력을 가져올 수 있다.
- 필수 필드가 없으면 AI를 호출하지 않는다.
- 조회 실패와 "대상 없음"이 구분된다.

**선행**: OPS-11

---

## [OPS-18] 출력 싱크(http·pubsub)

**목적**
결과를 사용자 시스템으로 돌려준다. **corral은 도메인 저장소를 만지지 않는다**(D8).

**범위**
- 인터페이스 + `http`(요청 템플릿) / `pubsub`(메시지 발행) 구현.
- 검증을 통과하지 못한 결과는 **내보내지 않는다**.
- 전송 실패는 실행 실패로 기록하고 재시도 정책을 따른다.

**수용 기준**
- 검증 통과 결과가 설정된 엔드포인트/토픽으로 전달된다.
- 저신뢰·검증 탈락 건은 전송되지 않고 이력에만 남는다.
- 전송 실패가 이력에 구분되어 남는다.

**선행**: OPS-08

# P5 — UI

## [OPS-19] 개발/운영 모드 분리

**목적**
한 앱에서 두 기둥을 오간다. 첫 화면에서 고르고, **마지막 선택을 기억**한다(D19).

**범위**
- 첫 화면: 개발 / 운영 선택.
- 마지막 선택 기억 후 다음 실행에 바로 진입.
- 헤더에 현재 모드를 **텍스트로 표시**하고 전환 수단을 둔다.
- 설정(프로바이더·상한 등)은 **공유**한다(D24).

**수용 기준**
- 재실행 시 마지막 모드로 진입한다.
- 헤더에 현재 모드가 보이고 전환된다.
- 설정 화면이 양쪽에서 동일하게 동작한다.

**선행**: OPS-01

---

## [OPS-20] 운영 대시보드 — 파이프라인 리스트

**목적**
운영 화면의 본체. **한 줄 = 파이프라인 하나**(D20).

**범위**
- 헤더: 오늘 사용량/상한(**공유 상한이라 항상 보여야 한다**), 트리거 연결 상태.
- 리스트 행: 활성 여부 · 이름 · 트리거→프로바이더 · 오늘 건수 · 처리 중/저신뢰/실패 · 수동 실행.
- 실행 상태는 이벤트 스트림으로 실시간 갱신.
- 파이프라인이 없을 때의 빈 상태(추가 유도).

**수용 기준**
- 등록된 파이프라인이 모두 보이고 상태가 실시간 갱신된다.
- 수동 실행 버튼이 동작한다.
- 상한 소진율이 헤더에 표시된다.

**선행**: OPS-19, OPS-08

---

## [OPS-21] 파이프라인 추가 팝업(3단계)

**목적**
사용자가 UI만으로 파이프라인을 만든다(D21~D23).

**범위**
- **1단계 이벤트 수신**: 트리거 종류 + 설정. **입력 조회 설정을 이 단계 안에 접어 넣는다**
  (본문 그대로 / 식별자로 조회 → 어댑터 설정). 단계를 4개로 늘리지 않는다.
- **2단계 AI 설정**: 모델·프로바이더·토큰 한도 + **프롬프트 + 출력 스키마 + 검증 규칙**.
- **3단계 결과 전송**: 싱크 종류 + 엔드포인트/토픽.
- 저장 시 정의를 검증하고, 실패 항목을 해당 단계에 표시한다.
- **수동 실행으로 즉시 테스트**할 수 있는 경로를 제공한다.

**수용 기준**
- 팝업만으로 파이프라인 하나를 만들어 저장·실행할 수 있다.
- 잘못된 입력이 저장 전에 걸러지고 어느 단계 문제인지 표시된다.
- 저장된 정의가 파일로도 확인·수정 가능하다.

**선행**: OPS-20, OPS-07

---

## [OPS-22] 파이프라인 상세 — 실행 이력·비용

**목적**
문제가 생겼을 때 **무슨 일이 있었는지** 볼 수 있어야 한다.

**범위**
- 최근 실행 목록(시간·결과·프로바이더·폴오버·토큰·소요시간), 결과별 필터.
- 실패·저신뢰 건의 사유 표시.
- 오늘/기간 집계(건수·토큰·비용).
- **저신뢰 건은 외부 검수 화면으로 딥링크**(D14). corral이 도메인 데이터를 그리지 않는다.

**수용 기준**
- 실행 이력이 최신순으로 보이고 필터가 동작한다.
- 실패 사유가 단계별로 구분되어 표시된다.
- 딥링크가 설정된 주소로 열린다.

**선행**: OPS-20, OPS-09

# P6 — 확장·검증

## [OPS-23] 코드 플러그인 탈출구

**목적**
선언으로 표현 못 하는 파이프라인이 반드시 나온다. **선언을 기본으로 두되 탈출구를 처음부터**
설계한다(D9, D10).

**범위**
- 플러그인 인터페이스: 입력 해석 / AI 단계 / 검증 / 출력 중 **필요한 지점만 교체**.
- 선언 정의에서 플러그인을 지정하는 방법.
- 플러그인 실행도 동일한 이력·상한·폴오버 정책을 따른다.

**수용 기준**
- 검증 단계만 코드로 교체한 파이프라인이 동작한다.
- 플러그인 실행이 이력·상한 집계에 동일하게 반영된다.

**선행**: OPS-13

## [OPS-24] 두 번째 파이프라인으로 선언형 검증

**목적**
**선언형이 어디까지 버티는지** 확인하는 가장 빠른 방법. 첫 파이프라인만으로는 일반화가
검증되지 않는다.

**범위**
- 성격이 다른 두 번째 파이프라인을 선언만으로 구성해 본다.
- 선언으로 안 되는 부분을 기록하고, **스키마를 넓힐지 / 플러그인으로 보낼지** 판단한다.
- 결과를 설계서에 반영한다.

**수용 기준**
- 두 번째 파이프라인이 코드 수정 없이(또는 플러그인만으로) 동작한다.
- 선언형의 한계가 문서로 정리된다.

**선행**: OPS-21, OPS-23
