# 설계서 — 운영 AI (Operational AI)

> 성격: **설계 결정서**. 학습·조사 기록은 `sdd-and-operational-ai-study.md`에 있고, 이 문서는
> 그 위에서 **확정된 결정과 그 근거**만 담는다. 코드는 아직 없다.
>
> ⚠️ **corral은 특정 프로젝트에 의존하지 않는다.** 이 문서에 등장하는 sojan/refinery는
> **첫 검증 사례**일 뿐이며, 스키마·어댑터·용어는 전부 도메인 중립으로 정의한다.

---

## 1. 무엇을 만드는가

corral에 **두 번째 기둥**을 세운다.

| | 개발 AI (기존) | **운영 AI (신규)** |
|---|---|---|
| 단위 | 이슈 1건 | **파이프라인 실행 1건** |
| 수명 | 수십 분 | 수 초 |
| 형태 | 멀티턴 + 도구 + 파일 핸드오프 | **1턴, 구조화 출력** |
| 결과 | Pull Request | 검증된 JSON → 외부로 전달 |
| 사람 | 계획·리뷰 승인 | 저신뢰 건 검수(외부 위임) |

운영 AI는 **"이벤트가 오면 → 데이터를 정제·분류하고 → 결과를 돌려주는"** 반복 작업을
corral이 실행·관제하는 것이다. 비즈니스 로직은 실행하지 않는다.

### 경계 (개념도 기준)

```
① 원천 데이터 ──이벤트──▶ ② 운영 AI ──▶ ③ 판단 ──▶ ④ 비즈니스 로직
   (사용자 시스템)        ★ corral      (사용자 코드)   (사용자 코드)
                            │
                       확신 낮으면 → 사람 검수(사용자 시스템)
```

**corral이 가져가는 것은 ②뿐이다.** ①③④는 사용자 시스템에 남는다.

## 2. 핵심 개념 — 파이프라인

사용자가 화면에서 다루는 단위는 **파이프라인**이다.

```
파이프라인 = [트리거] → [입력 해석] → [AI 오퍼레이션] → [출력]
```

| 구성 | 역할 | corral이 아는 것 | 사용자가 정하는 것 |
|---|---|---|---|
| **트리거** | 일감 수신 | 큐/HTTP/스케줄/수동이라는 **종류** | 어느 토픽·어느 주소 |
| **입력 해석** | 이벤트 → AI 입력 | "이벤트 본문 그대로" 또는 "**ID로 조회**"라는 방식 | 어느 URL·어느 필드 |
| **AI 오퍼레이션** | 프롬프트·스키마·검증 | 구조화 출력 + **범용 검증 규칙** | 프롬프트 문장·허용값·임계값 |
| **출력** | 결과 전달 | 큐/HTTP라는 **종류** | 어느 엔드포인트 |

**오퍼레이션**은 파이프라인 안의 AI 단계 하나를 가리킨다(입력→프롬프트→스키마→검증→결과).

## 3. 확정된 결정

### 3.1 배포·실행

| # | 결정 | 근거 |
|---|---|---|
| D1 | **VM 1대에 corral 1개** — 개발 AI·운영 AI 모두 여기서 실행 | 운영 AI는 상시 가동이어야 하고, 상한을 공유하려면 인스턴스가 하나여야 한다 |
| D2 | UI는 **원격 제어평면**을 신설해 접속 | ⚠️ 현재 corral은 **헤드리스로 못 돈다**(§6.1) |
| D3 | **로컬 데스크톱 앱 → 원격 코어** 방식을 우선. 브라우저 접속은 후순위 옵션 | 사용자가 브라우저 UI를 원치 않음. 두 방식은 **코어 작업을 공유**하므로 나중에 추가해도 낭비가 없다 |
| D4 | 접속은 **터널(SSH/Tailscale) 위**를 기본 전제 | 포트를 공개 인터넷에 열지 않는다 |

### 3.2 파이프라인 구성

| # | 결정 | 근거 |
|---|---|---|
| D5 | 트리거는 **큐 어댑터**가 기본, 첫 구현은 **Pub/Sub**. 스케줄·수동 실행 병행 | 포트를 열지 않아도 되고, 발행자가 구독자 위치를 모른다 |
| D6 | 입력은 **fetch-back** — 이벤트에는 식별자만 오고, corral이 **처리 시점에 조회**한다 | 큐 대기 중 원본이 바뀔 수 있다. 데이터를 실어 보내면 낡은 값으로 처리된다 |
| D7 | 조회 어댑터는 **`none`(이벤트 본문 사용)** + **`http`** 둘로 시작 | HTTP 하나가 REST·GraphQL·자체 API를 모두 덮는다(GraphQL은 `POST + JSON 본문`). DB 직접 연결은 저장소마다 어댑터가 늘고 결합도가 높아 두지 않는다 |
| D8 | 출력은 **메시지 발행 또는 API 호출**, 사용자가 설정 | corral은 도메인 스키마를 모른다. 결과를 저장하는 것은 사용자 시스템의 몫 |
| D9 | 오퍼레이션 정의는 **YAML 선언**으로만 한다 | 선언으로 안 되는 것이 나오면 **기능을 추가해서** 채운다. 사용자가 코드를 넣어 단계를 갈아끼우는 길은 두지 않는다 — 그러면 corral이 무엇인지가 그 파이프라인마다 달라진다 |

## 4. UI 설계

### 4.1 화면 구조

```
[첫 화면]  개발  |  운영          ← 마지막 선택 기억
                 │
        ┌────────┴────────┐
     [개발]              [운영]
   기존 대시보드      헤더: 모드 표시 · 오늘 사용량/상한 · 큐 상태
                     ─────────────────────────────────────
                     ● 파이프라인 A   pub/sub → claude · 오늘 128건   [실행]
                     ● 파이프라인 B   pub/sub → gemini · 오늘 30건    [실행]
                     ○ 파이프라인 C   http → gpt · 비활성             [실행]
                                                          [＋ 파이프라인 추가]
```

- **한 줄 = 파이프라인 하나**(D20). 표시: 활성 여부 · 이름 · 트리거→프로바이더 · 오늘 건수 ·
  처리 중 / 저신뢰 / 실패 수 · 수동 실행 버튼
- **상한은 헤더에 상시 노출** — 개발 AI가 공유 상한을 잠식하면 즉시 보여야 한다(D12)
- 클릭 → 상세: 실행 이력, 토큰·비용, 검수 대기 딥링크(D14)

### 4.2 파이프라인 추가 팝업 (D21)

```
1. 일감 수신
   이름 · 설명
   일감이 오는 방법:  (•) 내가 실행할 때만  ( ) 정해진 일정에  ( ) Pub/Sub 구독에서

2. 내용 가져오기                                   ← 자기 단계 (원래 ①에 접혀 있었다)
   이벤트에 실려 오는 것:
     ( ) 프롬프트에 필요한 내용이 다 들어 있음
     (•) id만 옴 — 나머지는 내 API에서 조회  →  method · URL 템플릿
   뽑아낼 필드 (이름: 경로) · 없으면 건너뛸 필드

3. AI가 할 일                                      ← D23
   프로바이더 · 최대 토큰
   프롬프트(시스템 · 사용자 템플릿)
   답의 모양(JSON Schema)
   답을 코드로 다시 검사: 개수 상한 · 최소 신뢰도

4. 결과 전송
   ( ) 어디에도 — 이력에만  (•) 내 API로  ( ) 토픽으로 발행
```

#### 왜 3단계에서 4단계로 바꿨나

D22는 "단계를 4개로 늘리지 않는다"였다. 3단계로 구현해 보니 **입력 조회가 접힌 채로
아무도 찾지 못했다** — 설계를 한 사람 본인이 못 찾았다.

세 가지가 겹쳤다: 기본이 접혀 있고, 큐를 골라도 그대로 접혀 있고, 문구(`내용은 어디서
가져오나`)에 "조회"도 "id"도 없었다.

**접는 것과 숨기는 것을 구분하지 못한 것이다.** 그리고 되짚어 보니 근거가 더 있었다:

- **스키마가 이미 4부분이다** — `trigger` / `input` / `agent` / `output`. `input`은
  트리거의 하위 설정이 아니라 동등한 최상위 축이다(D6/D7). 3단계는 4부분 모델을 3칸에
  우겨넣은 것이고, 그 압축의 대가를 `input`이 혼자 치렀다
- **오류 표시가 어긋났다** — 코어가 돌려주는 `input.*` 경로가 `key`·`trigger`와 같은
  칸으로 갔다. 이제 단계와 스키마 구획이 1:1이라 매핑 규칙 자체가 없다
- **분량이 고르지 않았다** — 1단계가 8필드를 넘겨서 접을 수밖에 없었다

대가는 "다음"을 한 번 더 누르는 것이고, 얻는 것은 fetch-back(D6)이 화면에 드러나는
것이다. **필수 결정이 숨겨진 3단계가 정직한 4단계보다 번거롭다.**

## 5. 파이프라인 스키마

> 구현됨 — `src/ops/pipeline/schema.ts`(정의) · `loader.ts`(적재). 아래는 실제 스키마다.
> 초안에서 바뀐 부분과 그 이유는 §5.2에 모았다.

도메인 용어를 쓰지 않는다. 아래는 **범용 이름**이며 어떤 프로젝트에도 적용된다.

### 5.1 정의

파이프라인 하나 = 파일 하나. `<상태 디렉터리>/pipelines/*.yaml`에 둔다.

```yaml
key: classify-record              # 식별자 (소문자·숫자·하이픈)
enabled: true
description: 들어온 레코드에 라벨을 붙인다
max_concurrent: 1                 # 이 파이프라인의 동시 실행 수

trigger:                          # ① 일감 수신 — manual | schedule | pubsub
  kind: pubsub
  topic: records.created
  subscription: corral-classify
  credential: { service: gcp, account: default }

input:                            # ①-하위: 이벤트 → AI 입력 — none | http
  kind: http
  request:
    method: GET
    url: "https://<host>/api/records/{{id}}"
    credential: { service: backend, account: default }
    timeout_ms: 15000
  select:                         # 응답 경로 → 납작한 입력 필드
    title:  "data.title"
    detail: { path: "data.description", truncate: 700 }   # 목록이면 limit: 20
  require: [title]                # 없으면 스킵(재시도해도 같은 결과다)
  skip_if: { field: "data.labels", is: non_empty }   # 이미 처리된 것 방어

agent:                            # ② AI 오퍼레이션 (1턴)
  provider: claude                # 생략하면 앱 전역 설정을 따른다
  max_tokens: 4096
  prompt:
    system: |
      <역할·규칙>
    user_template: |
      제목: {{title}}
      설명: {{detail}}
  schema:                         # 구조화 출력의 모양
    type: object
    properties:
      items:      { type: array, items: { type: string } }
      confidence: { type: number }
    required: [items, confidence]
  validate:                       # AI를 믿지 않는다 — 코드로 다시 검사
                                  # field는 위 properties에 선언된 이름이어야 하고,
                                  # 타입이 규칙과 맞아야 한다. 아니면 불러올 때 거부된다
    allowed_values:
      field: items
      source: { url: "https://<host>/api/vocabulary" }   # 또는 values: [...]
      select: "data.values"
    max_items:      { field: items, limit: 4 }
    min_confidence: { field: confidence, threshold: 0.7 }

output:                           # ③ 결과 전달 — none | http | pubsub
  kind: http
  request:
    method: PATCH
    url: "https://<host>/api/records/{{id}}"
    body: { labels: "{{items}}" }

on_low_confidence:                # 저신뢰 처리 (D14)
  action: report                  # report(보내지 않고 이력만) | skip | send
  review_url: "https://<host>/admin/records/{{id}}"
```

**`{{…}}` 치환 규칙**

| 쓰는 곳 | 결과 |
|---|---|
| `body: { labels: "{{items}}" }` — 자리표시자 하나뿐 | **값 그대로**. 배열은 배열로, 숫자는 숫자로 |
| `url: ".../records/{{id}}"` — 글자와 섞임 | 문자열 |
| `user_template`, `review_url`, 헤더 | 언제나 문자열. 배열·객체는 JSON으로 적힌다 |

받는 쪽 API가 `labels`를 배열로 선언했으면 배열이 가야 한다. 그래서 자리표시자 하나뿐인
칸은 문자열로 만들지 않는다. 없는 필드는 `""`가 아니라 `null`이다 — 빈 문자열은 그 자체로
값이라, 받는 쪽이 모델이 만든 값과 구분할 수 없다.

**설계 원칙**
- 필드 이름에 도메인 개념(태그·축제·카테고리)을 넣지 않는다
- 검증은 **AI를 믿지 않는다** — 프롬프트에 규칙을 적어도 코드에서 다시 검사한다
- 선언으로 표현할 수 있는 것은 **실행할 수 있는 것뿐**이다. 코드가 해석할 수 없는 문장은
  스키마에 넣지 않는다

### 5.2 초안에서 바뀐 것

만들면서 초안이 실행 불가능하거나 코드베이스 규칙과 어긋나는 지점이 드러났다.

| 초안 | 실제 | 왜 |
|---|---|---|
| `pipelines:` 를 corral.yaml에 | **`pipelines/` 디렉터리, 파일 하나당 하나** | 설정 마법사의 `buildConfigYaml`은 corral.yaml을 **매번 처음부터 다시 만든다**. 거기 두면 설정을 저장할 때마다 파이프라인이 지워진다. 파일 경계는 UI가 파이프라인을 쓰기 시작할 때 추가·삭제를 파일 하나의 문제로 만들어 준다 |
| 트리거 `pubsub\|http\|queue\|schedule\|manual` | **`manual\|schedule\|pubsub`** | 실행할 것이 없는 종류를 스키마에 두면 **영영 안 도는 파이프라인을 통과시킨다**. `http` 트리거는 포트를 열어야 해서 큐를 고른 이유(D5)와 정면으로 어긋나고, `queue`는 `pubsub`이 곧 그 구현이라 중복이다 |
| `skip_if: "…비어있지 않음"` | `skip_if: { field, is: empty\|non_empty }` | 자연어 조건은 코드가 실행할 수 없다 |
| `derive: "parent_of(items) 중복 제거"` | **없앰** | 임의 식은 선언으로 실행할 수 없다. 이런 파생이 실제로 필요해지면 **실행 가능한 형태의 기능으로** 추가한다 |
| `headers: { authorization: "Bearer ${SECRET}" }` | `credential: { service, account }` | corral은 설정 파일에 비밀을 두지 않는다. 어디서나 참조만 두고 값은 자격증명 저장소에서 온다 |
| `{id}` 와 `{{title}}` 혼용 | **`{{…}}` 하나로** | 두 문법을 둘 이유가 없다 |
| `max_concurrent`가 트리거 밑 | **파이프라인 밑** | 동시 실행 수는 *일이 어떻게 도착하는지*가 아니라 *일 자체*의 성질이다. 트리거 밑에 두면 수동 실행에는 한도가 없어진다 |

### 5.3 두 번째 파이프라인으로 확인한 것

파이프라인 하나가 돈다고 스키마가 일반적이라는 뜻은 아니다. 첫 파이프라인
(`classify-record`)은 네 축 모두에서 한쪽 구석만 밟았다 — 건당 이벤트, 단건 조회,
스칼라 답, HTTP 쓰기. 그래서 **반대쪽 구석**을 골라 선언만으로 세워 봤다.

```
schedule(주기)  →  http, 목록 조회  →  여러 건을 한 요약으로  →  pubsub 발행
```

실물은 `src/ops/pipeline/second-pipeline.test.ts`에 있다. 실제 HTTP 서버 둘과 진짜
1턴 실행기(제공자만 스텁)로 끝까지 돈다.

**돌리려고 새로 필요했던 것**

| | 무엇 | 성격 |
|---|---|---|
| 1 | 이벤트가 실은 입력 단계에서 사라지고 있었다. `select`가 **응답** 경로를 집는 순간 이벤트의 `{{id}}`·`{{scheduledAt}}`이 없어져서, 5.1 예시의 `PATCH .../records/{{id}}`가 `/records/`로 나갔다 | **결함**. 문서가 이미 된다고 가정하고 있었다 |
| 2 | 목록 개수 상한 `limit` | **기능 추가**. `truncate`가 긴 글에 하는 일을 긴 목록에 한다 |

나머지는 이미 됐다 — `skip_if`·`require`는 배열을 제대로 보고(빈 날은 1턴도 안 쓴다),
`max_items`·`min_confidence`는 요약 답에도 그대로 걸리고, 스케줄 틱의 `{{scheduledAt}}`은
조회 URL과 발행 메시지 양쪽에 쓰인다.

**선언으로 안 되는 것 (지금은 한계로 둔다)**

| 한계 | 우회 | 넓힌다면 |
|---|---|---|
| **시간 창을 못 만든다.** 틱은 `{{scheduledAt}}`(지금)만 준다. "어제부터"는 날짜 산술이고, 임의 식은 선언으로 실행할 수 없다 | 조회 URL이 상대 구간을 받게 한다 (`?window=1d`) | 템플릿 산술이 아니라 **트리거가 직전 발화 시각도 함께 주는** 형태. 실행 가능하고 식이 아니다 |
| **목록의 각 항목을 따로 검증할 수 없다.** `allowed_values`는 이름(문자열·숫자·불리언)만 비교한다. 객체 배열이면 불러올 때 거부되거나, 타입이 선언돼 있지 않았으면 실행이 `rejected`로 끝난다 | 검증할 값을 스칼라 배열로 답하게 한다 | 항목 안의 경로를 가리키는 형태 |
| **항목마다 한 번씩 돌릴 수 없다.** 파이프라인 하나 = 실행 하나 = 모델 1턴 | 목록을 펼쳐 이벤트로 만드는 건 사용자 시스템의 몫 | — 의도된 경계다. 1턴 고정이 운영 AI를 개발 AI와 갈라놓는 지점이다 |
| **`skip_if`는 조건 하나, `empty\|non_empty` 둘뿐** | 조회 URL의 쿼리로 거른다 | 조건을 늘리기 전에, 거르는 일이 조회 쪽에 있는 게 맞는지부터 |
| **출력은 하나.** 큐에 보내면서 동시에 API에도 쓸 수 없다 | 큐를 구독하는 쪽에서 한 번 더 | 목록형 출력 |

## 6. 선행 과제 (지금 구조로는 불가능한 것)

### 6.1 corral은 헤드리스로 돌지 않는다 ⚠️

- 헤드리스 엔트리(`src/main.ts`)가 없고 `start` 스크립트도 없다 — **README의 "Run headless"는 사실이 아니다**(수정 필요)
- 유일한 엔트리 `src/ipc-main.ts`는 **Electron이 IPC 채널로 fork**해야 제어가 된다.
  단독 실행하면 오케스트레이터는 뜨지만 승인·조작이 불가능하다
- renderer는 `window.corral`이 없으면 즉시 실패한다
- `WebChannel`은 이름과 달리 **HTTP 서버를 열지 않는다**(상태 보관용)

→ **원격 제어평면(WS + 페어링 인증)이 운영 AI보다 먼저 필요하다.**

### 6.2 네이티브 모듈을 늘리면 안 된다

- corral desktop은 **런타임 네이티브 의존성이 0**이라 Mac·Windows 크로스빌드가 단순하다
- 코어가 도는 Node 버전이 환경마다 다르다: **VM 헤드리스 = Node 24**(`node:sqlite` 가능),
  **데스크톱 = Electron 33의 Node 20**(불가)
- → 이력 저장소는 **JSONL**(D15). SQLite/DB는 인터페이스 뒤로 미룬다(D16)

### 6.3 원격 모드에서 네이티브 기능의 소재지

| 기능 | 향하는 곳 | 이유 |
|---|---|---|
| 설정·시크릿·방향성 | **원격(VM)** | 코어가 실제로 읽는 값 |
| Docker/CLI 감지 | **원격(VM)** | 워크스페이스가 거기서 돈다 |
| **프로바이더 로그인 캡처** | **로컬** | **로컬에는 브라우저가 있다** — VM의 OAuth 문제가 여기서 풀린다 |
| OS 알림 | 로컬 | 사용자가 보는 곳 |

시크릿은 키체인이 아니라 **환경변수 + 파일(0600)**로 해결된다 — 코어에 이미 구현돼 있다.
