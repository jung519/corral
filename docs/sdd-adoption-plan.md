# 작업계획서 — SDD 도입 (Spec-Driven Orchestration)

> 작성일: 2026-08-03 · 개정: 2026-08-24 (코드 대조 — §5 T2, §9, §13)
> 목표: **"SDD 개념을 도입한 AI 오케스트레이션"으로 corral을 대외 홍보할 수 있는 상태**로 만든다.
> 성격: 계획서(코드 없음). 확정/미결 구분 표기.
> 관련: `docs/direction-injection-plan.md`(선례 형식)

---

## 1. 목적

corral의 계획 단계(`pending_plan.md` 1개 문서)를 **requirements / design / tasks 3문서 + 단계별
승인 게이트**로 재구성하고, 수용 기준을 기계가 읽을 수 있는 형식으로 강제한다. 그 결과
"SDD를 쓴다"는 대외 표현이 **과장이 아닌 상태**가 되게 한다.

## 2. 배경 — 현재 구조

corral은 이미 **축소판 SDD를 돌리고 있다.** `WORKFLOW.md` 브랜치 A가 요구하는 것은
*바꿀 레포와 이유 · 접근 · 바꿀 파일 목록 · 엣지 케이스 · 테스트 가능한 수용 기준*으로,
Kiro의 3문서를 한 파일에 합쳐놓은 형태다.

부족한 것은 문서 개수가 아니라 **흐름·형식·연결** 세 가지다.

| 있는 것 | 없는 것 |
|---|---|
| 계획 문서 생성 + 사람 승인 | 단계별(요구사항/설계/태스크) 게이트 |
| 독립 비평 라운드(`plan-critique`) | 요구사항 **교차** 검토(모순·충돌·누락) |
| "testable acceptance criteria" 지시 | EARS 형식 강제 |
| 파일 핸드오프 인프라 | 요구사항 ID ↔ 태스크 추적성 |
| 정적 게이트 + 리뷰 라운드 | 리뷰가 **수용 기준을 대조**하는 층 |
| `implementing` 단일 페이즈 | 태스크 단위 진행 추적 |

## 3. 대외 표기의 정직성 선 (확정)

SDD는 Kiro 전유 용어가 아닌 **일반 용어**다(Kiro, GitHub Spec Kit 등 복수 제품이 사용).
따라서 "최초"·"독자적" 류의 선점 주장은 불가. 대신 **어디까지 했을 때 무엇을 말할 수 있는지**를
아래로 고정한다.

| 달성 수준 | 말할 수 있는 것 |
|---|---|
| 프롬프트 계층만 (§6) | *"spec-driven **planning**"* — 계획이 스펙 형식이다 |
| + 3단계 승인 게이트 (§5) | *"SDD 워크플로 지원"* |
| **+ tasks 상태 추적 (§5)** | **"spec-driven development"** — 온전한 표기 ✅ **목표선** |
| + 의존성 Wave 병렬 | Kiro 수준 (본 계획 비범위) |

> **원칙**: 구현되지 않은 층을 홍보 문구에 넣지 않는다. 세 번째 줄이 목표선이다.

## 4. 차별점 — Kiro와 무엇이 다른가 (홍보의 핵심)

SDD 자체는 차별점이 아니다. **SDD를 어디에 놓았는가**가 차별점이다.

| | Kiro | corral |
|---|---|---|
| 스펙의 출발점 | 개발자가 IDE에서 프롬프트 입력 | **트래커 이슈**(Notion/GitHub/Jira)에서 자동 생성 |
| 사람의 자리 | IDE 앞에 앉아 단계마다 대화 | **원격 승인만** — 대시보드/Slack |
| 실행 형태 | IDE 중심 (+CLI headless) | **무인 워커** — 폴러가 이슈를 집어 스스로 시작 |
| 모델 | 벤더 스택 + 크레딧 과금 | **BYOK**, provider×transport 6셀, 임베드 키 0 |
| 배포 | SaaS | **셀프호스팅**, Apache-2.0 |
| 범위 | 스펙 → 코드 | 스펙 → 코드 → 자기리뷰 → **멀티 레포 PR** |
| 고유 층 | — | **Direction(방향성)** — 조직 의도를 계획·리뷰에 주입 |

**한 줄 포지션(안)**:
> *"이슈를 넣으면 스펙이 나오고, 승인하면 PR이 나온다 — 내 키로, 내 서버에서."*

`Direction × Spec` 조합은 현재 확인 범위에서 corral 고유다 — **방향성(guiding) 위에 스펙(계약)을
얹고, 그 위에 skills(binding)를 두는 3층 구조.** 홍보 시 이 3층을 전면에 세울 것.

파일 셋만 빈 문자열로 덮는다.

```javascript
// src/orchestrator.ts — 각 dispatch가 자기 산출물만 선언한다 (CRL-88 이후)
dispatch(..., 'planning', [SCRATCH.pendingPlan])   // 계획을 쓰는 턴
dispatch(..., 'review',   [SCRATCH.pendingReview]) // 리뷰를 통합하는 턴
dispatch(..., 'implementation')                    // 읽기만 하는 턴 — 아무것도 안 지운다
```

지정 목록이지 디렉터리 청소가 아니므로 `.corral/spec/` 아래 파일은 애초에 대상이 아니다.
게다가 CRL-88 이후로는 **선언하지 않은 파일은 어느 턴도 건드리지 않는다.** 스펙 3문서는
아무 dispatch도 산출물로 선언하지 않는 한 그냥 살아 있다.

(초안을 `plan_draft.md`로 복사하는 코드는 그대로 있다. 통합 dispatch가 `pending_plan.md`를
새로 쓰기 때문이다.)

**T9/T10이 진짜 신규 엔진이다.** 나머지는 기존 구조의 재배치에 가깝다.

## 6. 프롬프트 / 문서 작업 (가장 싸고 체감 큼)

| # | 작업 | 내용 |

P1~P4는 **코드 수정 없이 프롬프트만 바꾸면 된다.** 여기부터 착수한다.

**검증이 2층에서 3층이 된다**: 정적 게이트(결정론) → 수용 기준 대조(스펙) → LLM 리뷰(판단).
정적 게이트를 맨 앞에 둔 기존 근거(*"LLM 리뷰어가 합리화로 무마할 수 없는 객관적 사실"*)가
수용 기준에도 그대로 적용된다.

**이 층이 잡지 않는 것 (2026-08-24 추가).** 수용 기준 대조는 *"무엇이 동작해야 하는가"* 를
확인한다. 실제 운영에서 반복해 나온 결함 둘은 그 축에 없다 — **주석·설계서가 코드와 어긋난
채 남는 것**(CRL-57, CRL-62에서 두 번), 그리고 **같은 파일을 연달아 고친 변경들이 서로를 안
보는 것**(CRL-49 ↔ CRL-60). 둘 다 수용 기준을 전부 충족해도 남는다. SDD가 이것까지 잡는다고
기대하지 않는다.

> **비범위**: property-based testing 자동 생성(Kiro 기능). 명시적으로 하지 않는다 — §14 참조.

## 9. ⚠️ 비용 영향 (반드시 먼저 검토할 것)

기본 설정(`rounds=1`) 기준 이슈 1건당 AI 호출 수:

| | 현재 | SDD 후 |
|---|---|---|
| 계획 단계 | 3회 (초안·비평·통합) | **9회** (문서 3종 × 초안·비평·통합) |
| 구현 | 1회 | **태스크 수만큼** |
| 리뷰·PR | 3회 | 3회 |
| **합계** | **7회** | **12회 + 태스크 수** |

태스크 5개면 **7 → 17회, 약 2.4배.** BYOK라 이 비용은 사용자가 직접 부담한다.

표는 `rounds=1` 기준이다. 리뷰 라운드는 설정값(`config/schema.ts`의 `rounds`)이므로 이 값을
올리면 배수도 같이 커진다 — 라운드는 SDD 전후 모두 붙지만, 늘어난 계획 단계 위에 곱해진다.

### ⚠️ 돈보다 먼저 걸리는 것 — 상한은 운영 AI와 공유한다

**계획서 작성(8/3) 뒤에 생긴 사실이다.** CRL-16(8/16)이 하루 토큰 상한을 개발·운영 **한 통으로**
합쳤다.

```
src/core/token-budget.ts   One daily token ceiling, shared by both pillars.
src/core-host.ts           ops.useBudget(budget)
```

선착순이고 한쪽이 소진하면 둘 다 멈춘다(D11/D12). 그리고 CRL-49 이후 운영 쪽 큐 트리거는
**상한이 차면 pull 자체를 멈춘다** — 일감을 안 가져가므로 유실은 없지만, 그동안 파이프라인은
아무것도 처리하지 않는다.

즉 SDD가 개발 쪽 호출을 2.4배로 늘리면 **그만큼 운영 파이프라인이 조용히 멈추고 큐가 쌓인다.**
개발자 한 사람이 이슈 몇 건을 돌리는 동안 하루 수천 건짜리 운영 흐름이 서는 그림이다.

경량 모드가 필요한 이유는 "비용이 는다"보다 이쪽이 무겁다. §17 미결 1번(`spec_mode` 기본값)의
근거도 여기로 옮긴다.

**대응(필수)**: Kiro가 Quick Spec을 만든 이유가 이것이다. corral도 **경량 모드**가 필요하다.

- `spec_mode: single` — 지금의 단일 계획서 유지 (기본값 후보)
- `spec_mode: split` — 3문서 + 3게이트
- 라벨 기반 자동 선택 (`heavy_labels`가 이미 있는 패턴 재사용)

**이 대응 없이 split을 기본값으로 밀면 비용·게이트 피로로 이탈한다.**

## 12. 단계

### S1 — 프롬프트 계층 (코드 변경 최소)
P1~P4 + T7(교차검토 대상 이동) + T12.
`WORKFLOW.md`와 프롬프트 상수만 손댄다. 파일은 여전히 `pending_plan.md` 1개.
- **DoD**: 생성된 계획의 수용 기준이 EARS 형식이고 REQ ID가 붙는다. 리뷰가 각 기준의 충족
  여부를 명시한다. 실제 이슈 1건으로 확인.
- 이 시점부터 *"spec-driven planning"* 표기 가능.

### S2 — 3문서 분할 + 게이트
T1~T6, T11, U1, U2, U5, P5.

## 16. 성공 기준 (전체 DoD)

1. 신규 사용자가 트래커 이슈 하나를 넣고, **요구사항 → 설계 → 태스크 → 구현 → PR**을
   대시보드 승인만으로 완주한다.
2. 생성된 `requirements.md`의 수용 기준이 EARS 형식이고, 리뷰가 **각 기준의 충족 여부를
   명시적으로 판정**한다.
3. 구현 중 대시보드에 **태스크 진행률**이 보이고, 앱을 껐다 켜도 남은 태스크부터 재개된다.
4. `spec_mode: single`로 기존 동작이 깨지지 않는다.
5. README·랜딩의 모든 SDD 관련 문구가 §3 표의 달성 수준을 넘지 않는다.
6. **도그푸드**: corral 자신의 이슈를 SDD 모드로 처리해 PR까지 완주한다.

### 미결 1번의 답 — `single` (2026-08-24, CRL-101)

근거 셋이 한 방향이고, 둘은 코드에서 확인했다.

**① 하루 상한이 두 기둥의 한 통이다.** `src/core/token-budget.ts` 첫 줄이 *"One daily token
ceiling, shared by both pillars"* 이고, 개발 쪽(`orchestrator.ts`)과 운영 쪽(`ops/ops-host.ts`
· `ops/pipeline/run.ts`)이 실제로 같은 것을 쓴다. 개발 호출이 2.4배가 되면 **돈을 더 쓰는
문제가 아니라 운영 파이프라인이 그만큼 멈추는 문제**다. §9 가 적어 둔 그대로다.

**② 진행 중 이슈.** `split` 이 기본이면 §10 의 마이그레이션이 필수 작업으로 붙는다. 계획
문서가 스스로 그렇게 적었고, 이 저장소도 지금 이슈가 돌고 있다.

**③ 되돌릴 수 있는 방향.** `single` 이 기본이면 켜는 것이 선택이고, `split` 이 기본이면 끄는
것이 사후 대응이 된다. 아직 실사용 한 바퀴(§16)를 안 돈 기능의 기본값으로는 앞이 맞다.

**이 결정이 미결 3번과 CRL-110 의 자리도 정한다.** 기본이 `single` 이면 아무도 자동으로
2.4배를 쓰지 않으므로, 운영 AI 상한 완화(CRL-110)는 S3 뒤로 가도 된다. `split` 을 기본으로
바꾸는 날 그 작업이 선행 조건이 된다.

### 미결 4번의 답 — 강제 (2026-08-24, CRL-98)

**실측했다.** 같은 이슈(CRL-89)로 브랜치 A를 두 번 돌렸다. 오케스트레이터를 태우지 않고
실제 `renderWorkflow` 로 가이드를 렌더해 실제 CLI 에 넘긴 뒤 나온 `pending_plan.md` 를 읽었다.

| | claude | codex |
|---|---|---|
| 수용 기준이 EARS 형식 | **4/4** | **4/4** |
| `REQ-n` 부여 | 4/4 | 4/4 |
| 다른 절의 ID 참조 | 18줄 | 15줄 |
| 형태 분포 | 상시 1 · 사건 2 · 오류 1 | 상시 2 · 사건 1 · 오류 1 |
| 소요 · 비용 | 321초 · \$3.08 | 159초 |

**둘 다 100% 다.** 형식을 못 써서 완화해야 할 상황은 오지 않았으니 템플릿을 그대로 강제한다.

**형태 선택이 더 중요한 결과다.** 네 요구사항 중 셋에서 두 CLI 가 같은 형태를 골랐다 —
문서 내용에 대한 요구사항은 상시형, 오류 경로는 `IF … THEN`, 컨테이너 생성은 사건형.
갈린 하나(REQ-2)는 claude 가 `WHEN the guide instructs branch C` 로 썼는데 이건 실행 시점의
사건이 아니라 문서 위치라 상시형이 맞고, codex 가 그렇게 썼다. 8번의 선택 중 7번이 적절했다.

**§6 P1 대로 `WHEN` 하나만 줬다면 이 결과가 안 나온다.** 두 CLI 모두 조건 없는 요구사항에
상시형을, 오류 경로에 `IF … THEN` 을 골랐다. 그 형태들이 없었으면 억지 `WHEN` 문장이 됐을
것이고, 그러면 *"AI 가 EARS 를 쓸 줄 아는가"* 대신 *"템플릿이 안 맞는가"* 를 잰 셈이 된다.
그래서 CRL-98 은 P1 을 다섯 형태로 넓혀 구현했다.

**형식을 검사하는 코드는 아직 만들지 않는다.** 2/2 가 통과했으니 검사기가 잡을 실패의 근거가
없다. 예비 이슈로 남겨 두고, CRL-34 사다리 실사용에서 형식이 깨지는 것이 관측되면 그때 만든다.

**이 결론의 한계.** n=2 이고 **이슈는 하나**다 — 그것도 오류수정 이슈다. 두 번째 실행을
다른 이슈가 아니라 다른 provider 에 쓴 것은 corral 이 provider 중립이어서, "표기법을 따르는
능력이 provider 에 달렸는가" 가 이슈 종류보다 판단에 무겁다고 봤기 때문이다. 기능추가 계획의
EARS 는 아직 안 봤다. P6(Bugfix 스펙)이 다루는 *"변하면 안 되는 것"* 축도 이번 측정 밖이다.
